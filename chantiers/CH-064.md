# CH-064 — Ariane réécrite en Rust (programme, par étapes) (06/11/2026)

Ordre de l'opérateur (06/11, D-291) : « ouvrir et piloter le chantier de la réécriture d'Ariane (basé sur les dernières versions) en Rust. Nous continuons avec nos versions en JavaScript en attendant l'avancement de ce chantier. »

Branche `chantier/CH-064` depuis `claude/50-test17`. C'est un PROGRAMME de plusieurs étapes, piloté par l'intégrateur. Chaque étape a son jalon et sa preuve. Lire d'abord :
- `CLAUDE.md`, `fiches/PASSATION_SESSION.md` ;
- `chantiers/CH-061.md` et son rapport (branche `chantier/CH-061`) : bancs JS contre Rust/WASM déjà mesurés, outillage `wasm32-unknown-unknown`.

## Principes (non négociables)
1. **Le JavaScript reste la production.** Rien du code Rust n'entre dans le paquet tant que l'opérateur ne l'a pas décidé par écrit, module par module. Le tronc JS continue d'évoluer : la réécriture suit ses dernières versions, comme cible mouvante.
2. **Ce qu'une extension Chrome impose.**
   - Les API `chrome.*`, le DOM, la page ESV, IndexedDB et `chrome.storage` restent appelés par du JavaScript.
   - Le Rust compilé en WebAssembly porte le cœur : lecture du LiDAR, géométrie et décision de pose, lot, relecture, état et journal.
   - Une coquille JS mince fait le lien.
   - L'architecture cible est à écrire et à justifier en étape 1.
3. **Identité prouvée, octet pour octet.** Chaque module Rust donne EXACTEMENT les mêmes sorties que le module JS qu'il remplace, sur les données réelles (nuages, journaux, fixtures des essais) : mêmes poses au millimètre, mêmes décisions, mêmes événements, mêmes exports. Un banc de parité JS contre Rust est tenu à jour pour chaque module.
4. **Essais.** Les essais JS existants (~3 170) restent la référence. Chaque module porté a ses essais Rust (`cargo test`) et passe la parité contre le module JS.
5. **Mesure.** Pour chaque module, temps et mémoire JS contre Rust/WASM, dans un vrai Chromium (`/opt/pw-browsers/chromium`), coût de traversée JS ↔ WASM compris. ÉTABLI / PROBABLE / SUPPOSÉ.

## Étapes (une étape = un jalon = un rapport court)
1. **Architecture et outillage** :
   - un espace Cargo `ariane-rs/` à la racine du dépôt, hors paquet (vérifier `tools/package.py`) ;
   - la cible WASM et la coquille JS ;
   - le format des échanges JS ↔ WASM ;
   - la carte des modules JS → crates, avec l'ordre de portage justifié : d'abord les modules purs, et ceux où CH-061 mesure un gain ;
   - le banc de parité générique (rejouer un module JS et son port Rust sur les mêmes entrées, comparer les sorties) ;
   - ce qui reste en JS et pourquoi.
   - Le plan est soumis à l'intégrateur avant de porter quoi que ce soit.
2. **Premier module pur porté** (proposé : géométrie et pose, `src/geometry*.js`, déjà prototypé par CH-061) :
   - parité bit à bit sur tous les nuages réels disponibles ;
   - banc ;
   - essais.
3. **Modules purs suivants**, dans l'ordre de l'étape 1 : lecture LiDAR, décision du lot, GCV1/GCV2, relecture (sélection, critère, signal), état en morceaux, index du journal…
4. **Branchement expérimental** : une construction séparée de l'extension (jamais le paquet livré) où la coquille JS appelle le cœur WASM, avec la maquette ESV et la parité de la relecture et du lot.
5. **Bilan pour décision de l'opérateur** : gains mesurés poste par poste, risques, et ce qui serait prêt à remplacer le JS.

- Aucune requête vers le vrai ESV. Aucune écriture dans ESV.

## Étape 1 bis — Option B : extension mince et programme Rust natif sur le PC (ordre de l'opérateur, 06/11)
Comparer deux architectures :
- **A** : une extension MV3 avec un cœur Rust en WebAssembly ;
- **B** : une extension MV3 mince, qui ne fait que lire la page ESV, cliquer et valider, et un programme Rust natif sous Windows, joint par `chrome.runtime.connectNative` (native messaging). Le programme porte le calcul, la décision, l'état et le journal.

Mesurer dans un vrai Chromium, sur les données réelles de `banane-data` (04/11 et 05/11) :
1. la latence d'un aller-retour par message, et le débit pour une capture LiDAR de 500 000 points ;
2. le temps du calcul de la pose et de la lecture LiDAR en natif, contre WASM et JS ;
3. la mémoire : celle de Chrome, celle du programme, et ce qui est rendu au système ;
4. la tenue quand Chrome endort le service worker, quand le programme s'arrête, et quand Chrome redémarre ;
5. l'installation sous Windows :
   - manifeste du programme natif, clé de registre, droits administrateur ou non ;
   - mise à jour et désinstallation ;
   - ce qu'un poste d'entreprise peut bloquer (stratégies de groupe, liste blanche d'hôtes natifs, antivirus).

Règles :
- Parité octet pour octet avec le JS, comme pour A.
- Rien dans `src/` ni dans le paquet : tout dans `ariane-rs/` et `chantiers/CH-064/`.
- Aucune requête vers le vrai ESV.
- ÉTABLI / PROBABLE / SUPPOSÉ. Le conteneur est sous Linux : ce qui est propre à Windows, et ne peut pas y être mesuré, est marqué SUPPOSÉ, avec sa source.
